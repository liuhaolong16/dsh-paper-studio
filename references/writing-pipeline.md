# 初稿生产流水线（S0–S7）· 从真实 run 抽出

> 来源：`<playbook 仓>\run\2026-10-10-NASA电池SOH预测\` 的**真实产物形态**（不是设想）。
> 用法：`node bin/studio.cjs scaffold --out <目录> --name <稿名>` 会按本流水线生成阶段文件骨架。
> 真源：本文件与 `pipeline.json` 的 `write` 链路配合；阶段产物名与必填字段以本文件为准。

## 0. 为什么要有这条流水线

第一稿是**一步步攒出来的**（输入 → 检索 → 选题 → 大纲 → 数据方法 → 正文 → 成品件 → 投稿材料），
每一步留下一个**带编号的文件**。好处是：断点可续、缺口可查、门可以按阶段挂。
**别跳步**：跳过的步骤最后都会以"返工"的形式回来（真实例：结果没定先写引言 ⇒ 两节重写）。

| 阶段 | 产物（真实文件名形态） | 必填交接字段 | 挂哪道门 | 该阶段的坑（见 `lessons-from-first-draft.md`） |
|---|---|---|---|---|
| **S0 输入** | `00-输入.md` | 研究问题 · 已有材料 · 数据可得性 · 目标刊/学位要求 · 语言 | — | 材料没盘点就开写 ⇒ 后面反复补 |
| **S1 检索证据** | `01-检索证据.md` + `_refs/fulltext/` + `锚点读原文记录*.md` | 每条引用的 DOI · 标题（**机器读过**）· 全文状态四分类 | 引用锚点门 | 「标了 OA ≠ 能读到正文」；二手页码必须删（L-4/L-5） |
| **S2 选题** | `02-选题.md` | 一句话 claim · 贡献三条 · 缺口句 | — | 无实验条件下的选题形态要先定（见 `无实验条件下的选题与创新形态.md`） |

| **S4 数据与方法** | `04-数据方法.md` + 数据核实记录（`05-缺陷核实-*` `07-数据质量核实` `08-筛选判据修正`） | 数据口径 · 筛选判据 · 随机种子与稳健性 · 误差棒定义 | 契约门 | **口径先核实**（温度口径那类缺陷会在结果里放大）；种子稳健性要跑（L-7） |

## 2. 硬纪律（跨阶段，全部由真实事故换来）

1. **先填结果，再倒填引言与摘要。**
2. **工作注记与主稿物理分开**：主稿只留可提交内容；`⚠ / Must be confirmed / TO BE COMPLETED` 一律不留在正文。
3. **每条引用只收录"机器读过标题"的条目**；不凭模型记忆或二手引文表填 DOI。
4. **全文状态四分类**：`full_text_read` / `paywall_page` / `image_only` / `download_failed`；**后三类一律不得当"读过全文"**（判据：下载成功 + 抽到文字层 + 付费墙标记命中 <2）。
5. **改"正文里的某种约定"前，先列出所有读它的人**（Word 转换器、契约门、引用门、成品核验器…），改完逐个回归。
6. **阶段产物带编号且不覆盖**：新一版开新号（`-v2`），旧版留档 —— 与"淘汰只由人决定"一致。

## 3. 与门的关系

```
scaffold（生成 S0–S7 骨架）
   → 逐阶段填写 → run-gates（六道门，按 pipeline.json）
   → report（待修项清单，带行号）
```

门是**阶段的检查点**，不是流水线本身：写完 S5 就该跑契约门/引用锚点门/语言门；做完 S6 再跑成品件核验与同步门。
