## 三、我们**现在用文字形态实现**的交互（UI 化候选）

这些做法已经存在，只是**以文本/工具调用形态**呈现；若做 UI，它们是第一批值得上屏的对象：

1. **点击式选项**（已用 `ask_user_question`：单/多选、推荐项置顶并标「（推荐）」、每项一行小字说明代价）——最接近"原生 UI 交互"的一处。
2. **决策卡**：一次一个决策 + 一行小字解释后果（CLI 等价物＝`form ask` 的四问门）。
3. **门的读数卡**：红/绿 + **为什么** + **怎么修**（等价物＝`gates`/`preflight`/`package-audit` 的输出）。
4. **进度与槽位可视化**：时间盒、逐节预算、幻灯片槽位（等价物＝`talk` / `form budget`）。
5. **评分与置信滑块**：审稿分诊的严重度×成本、跨模型评分与置信标签（等价物＝`reviewers`）。
6. **一键复跑**：把"可复跑命令"变成按钮（等价物＝白板里那份命令清单；与我们既有的「只有用户能做的动作要做成可双击文件」同源）。
7. **归属与许可看板**：A 栏（须署名）/ B 栏（致意）+ 机器校验结果（等价物＝`license-audit` 的归属面）。

## 四、启用前提（**这是当初暂缓的真实原因，必须先满足**）

若日后决定做 UI 主入口，下面每一条都要有实证，否则就是重演白屏：

- [ ] **静态锁**：客户端半体必须被自家检查器判否（`panel/_check-client.cjs` 须含**必失败臂**，不能只有正控）。
- [ ] **桩宿主预演**：`preview-host.cjs` 必须真跑宿主半体并给出非空页面证据（历史读数 4/4 PASS）。
- [ ] **热更新纪律**：客户端插件改动只有在 `pnpm run dev:web` 同时运行时才会自动重载；否则**必须重建 + 刷新页面**，不许假设"改了就好了"。
- [ ] **隔离与回落**：UI 缺失时 CLI 全功能可用；UI 崩了不得拖垮主链路（缺 panel ⇒ 记 SKIP，不是 PASS，也不是失败）。
- [ ] **回滚点**：每次上 UI 前打回滚点 + 明确回滚命令。
- [ ] **崩溃归因顺序**：安装日志 → `node_modules` mtime 倒序 → WER → 会话日志 → 时间戳对齐（既有铁律 4）。
- [ ] **不在宿主运行中装/卸/升级**（既有铁律 1）。

## 五、触发重新评估的条件（写给未来的自己）

满足任一即可向用户提议"试一版 UI"：① 上述前提全部有实证；② 用户主动提出要做 UI；③ 出现"纯文本形态明显吃亏"的场景（例如多轮决策密集、需要一眼看全局状态的评审/投稿流程）。
